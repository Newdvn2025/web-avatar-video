# 处理与集成

## 本案例参数
环绕源视频：视频节点6.mp4，834×1112，12.041667秒，提取12fps，共145帧。坐标以页面视口中心为原点。实际标定键（0起始帧索引）：

|方向|左|左上|上|右上|右|右下|下|左下|左|
|---|---|---|---|---|---|---|---|---|---|
|索引|15|28|42|53|64|76|86|100|109|

帧索引15对应文件frame-016.webp，避免0起始/1起始混淆。第0帧为正面。方向键是本次近似标定，不能当作新视频的标准答案。

三个滚动动作：视频节点1、2、3，834×1112，各约6.04秒，12fps，各73帧。

## 批处理
需要 macOS14+（Vision前景分割）、Swift命令行工具、ffmpeg/ffprobe、Python与Pillow。本次实际使用macOS26.5.2。只检查依赖；缺少时说明，不静默安装。

```sh
python3 scripts/prepare_frames.py /absolute/path/video.mp4 /absolute/path/output --fps 12
```

脚本以临时目录提取原尺寸PNG，运行Vision前景掩膜，轻微收缩掩膜及羽化边缘，输出透明WebP和manifest.json；输出目录非空时拒绝覆盖。前景分割会保留其他被识别的前景物体，必须人工检查。小点若覆盖人物，普通抠图无法解决。

抽帧查看：
```sh
ffmpeg -i input.mp4 -vf 'fps=1,scale=180:240,tile=4x3' -frames:v 1 contact.jpg
```
12fps是本案例体积与动作密度的折中，不是通用硬要求。先原分辨率处理，再看是否需要尺寸调整；不用压低分辨率后宣称原视频模糊。

## 代码改动位置
`assets/demo/avatar.js`：
- canvas.width/height：改成源尺寸。
- loadSequence("orbit",145,"webp")：改素材数量和路径。
- orbitFrame() 的 keys：按实际视频重新标定。
- ensureSequence()：本案例动作均为73帧；不同数量需改为配置数组。
- actionTarget：滚动进度映射，当前是章节顶部到达视口中部后开始，0.9章高度完成。
- CSS只控制人物构图与颜色，不代替视频里的姿态运动。

角度 atan2(dy,dx) 映射环周，按相邻方向键插值得到帧。环周平滑用最短角差，避免左侧边界从末尾倒着跑一整圈。中心静止区半径0.16归正；离开窗口归正。其余半径不控制动作幅度。中心跨入外圈会从正面切到该方向，可能有跳变。

别把透明帧之间直接交叉淡化当成姿态插值：会产生双眼、重影。正反播放和跨边界也须实际检查。

## 性能与排错
Demo使用透明WebP，环绕145帧，动作219帧。实际文件体积见交付validation.json。浏览器解码后的RGBA内存远大于文件体积：全部364帧解码理论约1.35GB，浏览器缓存行为会变化。当前按章节延迟加载、预加载下一幕，不适合直接声称已做生产级低内存优化。

生产交付按需改成限帧缓存、减少帧数、分章节释放资源或支持透明视频的多格式方案。WebP节省下载并不等于节省解码内存。

Canvas不能同时创建2D和WebGL上下文。页面只加载一个控制脚本，移除旧3D脚本，避免“已有不同类型上下文”的错误。HTTP运行不要用file://。相对路径适配子目录；文件缺失不应长期用错误方向的第一帧掩盖，要检查网络404。

触屏第一幕静态；减少动态偏好全幕静态。演示保留原动作，而不是在系统减少动态时继续播放。
